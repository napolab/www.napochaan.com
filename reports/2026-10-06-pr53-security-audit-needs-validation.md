## N1. Password written via REST while Access-only auth is active survives Access revocation and becomes a live local credential after rollback

- fingerprint: `payload-cloudflare-access/plugin/withAccessAuth/enableFields-password-write-survives-access-revocation`

### 主張する根本原因

withAccessAuth (packages/payload-cloudflare-access/src/plugin/index.ts:45-56) keeps the local auth columns with disableLocalStrategy: { enableFields: true } so that rollback works. Payload's updateDocument treats enableFields as permission to hash and persist data.password (update.js:26,30,231-240). The plugin installs no collection beforeOperation hook (the only hook that runs before update.js:26 captures the password) that rejects password for update operations while Access is enabled. Nothing in the plugin or the rollback runbook invalidates salt/hash written during the Access-only window when the config goes back to local auth. Fix direction: in withAccessAuth, prepend a hooks.beforeOperation entry that throws a Forbidden/ValidationError when operation is 'update' (also 'create'/'forgotPassword'/'resetPassword' for defense in depth) and args.data has a password key, plus a regression test. A beforeChange strip is insufficient because the password was already captured. Also add a rollback step that nulls salt/hash for every user except the owner, or that audits users whose hash is non-null, before CF*ACCESS*\* is removed.

### 説明

When the Cloudflare Access plugin is enabled, withAccessAuth sets disableLocalStrategy: { enableFields: true } on the users collection and adds no hook. In Payload 3.84.1, updateDocument captures data.password from the raw request data. With enableFields it still computes shouldSavePassword=true and writes salt/hash into the update after the field-level access checks have run. So the hidden salt/hash fields' access.update:false never applies. users.update is `user !== null` with no ownership check, so any Access-admitted session can PATCH /api/users/:id (or bulk PATCH /api/users?where=...) with {"password":...} on any user record. That includes a password-less user the session auto-created for itself or created via POST /api/users. The admin edit view (Change Password hidden under disableLocalStrategy) and GraphQL (no password input unless optionalPassword) do not offer this write. create.js does not hash under disableLocalStrategy. REST/Local update is the one open door. While Access is on, the hash is dormant: loginOperation throws Forbidden and local-jwt is not registered. The documented rollback (remove CF*ACCESS*\* and deploy) restores password login and the local-jwt strategy. A hash planted during the Access window then authenticates as a full admin, because collections have no roles. Removing that identity from the Access policy or logging it out of Access does not invalidate the planted password. salt/hash are hidden, so the owner cannot see which users carry one, and the rollback runbook assumes auto-created users have no password and has no step to audit or clear them. The writer is already an admin when it writes, so the defect is a credential that outlives revocation, not a privilege gain at write time. Under the runbook policy (owner email only), the writer must be a broadened-policy identity or someone holding a compromised owner Access session.

## N2. stg CF_ACCESS_AUD list makes the pre-existing host-wide Access app's policy a full-admin boundary for the stg Payload REST API

- fingerprint: `payload-cloudflare-access:verify:aud-any-of-accepts-stg-host-wide-app-as-admin`

### 主張する根本原因

Audience binding is any-of over a configured list (jose `audience: [...aud]`) with no per-AUD distinction between the owner-only admin path app and the broader stg host-wide app, and the app has no in-app authorization (no roles or email allowlist; auto-provisioning with overrideAccess; rules are `user !== null`). The staging runbook adds the host-wide app's AUD to that list without requiring the host-wide app's policy to be owner-only.

### 説明

verifyAccessJWT accepts any app-type token with a non-empty email whose aud matches any entry of the CF*ACCESS_AUD list. Every accepted email is found or auto-created as a role-less users document (overrideAccess: true), and every collection/global write rule is `user !== null`, so the resolved user is a full Payload admin. The runbook tells the operator to put the AUD of the pre-existing stg host-wide Access application into the stg list next to the new path app, but only requires an owner-email-only policy for the new /admin* and /oauth/authorize* path apps; the host-wide app's policy is left as is and never constrained. Per the runbook, the host-wide app also covers stg /api/* and injects Cf-Access-Jwt-Assertion there. Once Access is enabled on stg, any identity admitted by the host-wide app (a group, an email domain, Everyone/OTP, a collaborator email) would get a header token carrying the listed host-wide AUD on /api/\_, pass the header CSRF rule with a non-browser client or a same-origin request, and become a Payload admin through the REST/GraphQL API: create/update/delete blog, works, news, logs, gallery, media, profile and users on stg. Verifier correction: the hunters' claim that such a user could also approve MCP OAuth grants on /oauth/authorize, or use the /admin UI, is not supported by source; per the runbook those paths sit under the more specific owner-only path app, so a non-owner would be stopped at the edge there (this edge precedence is itself a deployment fact). The exposure is limited to stg and exists only after the runbook's stg enablement; prod lists only the path app AUD.

## N3. Runbook's optional stg /api\* Access Bypass app is not reverted by the rollback procedure, leaving stg Payload password login internet-reachable (possibly with dev seed credentials)

- fingerprint: `docs/cloudflare-access.md:stg-api-bypass-outlives-rollback-password-login`

### 主張する根本原因

The runbook adds an optional, persistent edge-config change (a Bypass app on stg.napochaan.com/api\*). Its safety depends on the plugin being enabled (disableLocalStrategy), but the rollback procedure that disables the plugin and re-enables password login does not revert that edge change. The 'same exposure as prod' equivalence also ignores that stg may hold dev-seed credentials (seed:import creates dev@napochaan.com with the default 'password'), while prod's seed path never creates a user.

### 説明

While the plugin is enabled this is safe: withAccessAuth sets disableLocalStrategy {enableFields:true} (plugin/index.ts:53) and Payload 3.84.1 loginOperation throws Forbidden when disableLocalStrategy is truthy (login.js:31). The rollback section (lines 199-206) only removes CF_ACCESS_TEAM_DOMAIN / CF_ACCESS_AUD and states that email + password login comes back (line 203). It has no step that deletes the /api* Bypass app, and line 206 makes rollback the recovery path for a botched enablement, which is when a stg test Bypass is most likely to be present. The same state also occurs if the plugin silently disables on stg (one var empty, lines 25-26). In that state the worker guards only /api/mcp (worker/app.ts:38), the Payload REST POST handler serves /api/users/login, and a returned token is accepted on all stg /api/* via 'Authorization: JWT' with no Origin check (extractJWT.js:39). The staging skill lists CLOUDFLARE_ENV=staging pnpm seed:import (SKILL.md:31), and its ensureAdminUser creates dev@napochaan.com with a password that defaults to 'password' (import.ts:25-26,56). Prod's seed:import:prod deliberately creates no user (import-prod.ts:7-13). Runbook step 1 (line 40) also keeps a password on the owner's stg user. Mitigations that bound but do not remove the risk: the Bypass is optional and the runbook flags the exposure as the owner's decision; SKILL.md:15 restricts seed:import to explicit requests; Payload's default lockout is 5 attempts / 10 min (defaults.js:124-126), which does not stop a single correct guess of a known default. Impact is limited to staging: separate D1/R2/OAUTH_KV bindings (wrangler.toml:110,115 vs 177,182), so the result is full admin CRUD over stg collections, users, media and stg MCP grants, not prod. Realization depends entirely on deployment facts that are not in source.

## N4. Header-source CSRF rule authenticates cross-site top-level GETs (and same-site subresource GETs), letting another site trigger Payload admin GET-render writes (empty autosave drafts, list-preference upserts)

- fingerprint: `payload-cloudflare-access/csrf/isAllowedHeaderRequest:cross-site-document-get-admin-side-effects`

### 主張する根本原因

packages/payload-cloudflare-access/src/csrf/index.ts:33-35 treats every Origin-less request whose Sec-Fetch-Site is not 'cross-site' (including same-site subresources), and every cross-site request with Sec-Fetch-Dest 'document', as safe for the ambient Access header token. There is no path, method-intent or user-activation restriction, so the allowance covers the whole host instead of only the two landing flows that need it. Payload's admin RSC views write state during GET renders: autosave create-on-render and list preference upsert. They rely on the baseline cookie rule rejecting cross-site Origin-less requests, a request shape the header rule now authenticates.

### 説明

For a token taken from Cf-Access-Jwt-Assertion, isAllowedHeaderRequest allows a request with no Origin when Sec-Fetch-Site is anything other than 'cross-site' (csrf/index.ts:33), and allows a cross-site request with no Origin when Sec-Fetch-Dest is 'document' (csrf/index.ts:35). Neither branch checks the path or Sec-Fetch-User. The relaxation exists for two flows: the post-Access-login landing on /admin and the claude.ai popup to /oauth/authorize. Because it is host-wide, it also authenticates any cross-site top-level navigation into the admin, including one started by script (window.location, a link, or a GET form). Payload 3.84.1's own cookie rule (extractJWT.js:30-37) rejects that request shape, so before this PR such a navigation reached the admin unauthenticated. Two admin RSC GET renders write server state. First, Document/index.js:245-271: for a collection with autosave, no versions.drafts.validate, and create permission, rendering /admin/collections/<slug>/create calls payload.create({data: {}, draft: true}) and then redirects. blog, news, works, gallery and logs all use autosave with create: user !== null, and the page route passes no initialData, so an empty draft is inserted. Second, List/index.js:68-80: the list view upserts the user's payload-preferences (columns, groupBy, limit, preset, sort) from query parameters. The chain needs the plugin enabled and Access to inject Cf-Access-Jwt-Assertion on a top-level GET. The runbook (docs/cloudflare-access.md:57-62) places /admin* under an Access path app with a SameSite=Lax cookie, and Lax still sends the cookie on top-level GETs. Under those conditions, a page on another site can make the logged-in owner's browser create an empty blog/news/works/gallery/logs draft, or overwrite their saved list view settings, once per top-level navigation. The response is not readable cross-origin. Each navigation hands control to napochaan.com, so the attacker gets one write per navigation: redirecting the attacker's own tab needs no user activation but ends the attacker page, and each additional popup needs a user activation. REST mutations stay blocked: they need POST/PATCH/DELETE, which carry an Origin that hits the allowlist. The consent server action is also blocked, by Next's Origin/Host check plus the allowlist. Parent-requested variant: line 33 also allows Sec-Fetch-Site 'same-site' with any destination, so an <img> or other subresource GET from a sibling *.napochaan.com host (e.g. stg.napochaan.com) reaches the same sinks. Payload's baseline cookie rule also accepts same-site, so that variant matches the baseline and needs attacker control of a sibling subdomain. The cross-site document case is the new exposure. Impact is integrity-only and low: junk draft rows (and their version rows) in the admin, plus admin UI preference tampering. The collections' afterChange revalidation hooks run but do nothing for these rows, because they only purge caches when the published state is touched (hooks/revalidate/index.ts:102-103), so the public site is unaffected. No disclosure, no publish, no privilege change. A source fix would limit the cross-site-document allowance to the landing paths that need it (/admin exact root or the Access callback landing, and /oauth/authorize). Alternatively, require Sec-Fetch-User: ?1 there and reject the cross-site document case for /admin/collections/\*/create and list routes, or send cross-site admin navigations through a same-origin interstitial before any authenticated render.

### ソーストレース

1. **entrypoint** `node_modules/@payloadcms/next/dist/utilities/initReq.js:42` (initReq (admin RSC GET render via src/app/(payload)/admin/[[...segments]]/page.tsx)) — A cross-site top-level GET to /admin/collections/blog/create is authenticated by passing the incoming request headers, including the Access-injected Cf-Access-Jwt-Assertion, to executeAuthStrategies.
2. **propagation** `packages/payload-cloudflare-access/src/strategy/index.ts:42` (requireSafeOrigin) — extractAccessToken tries the header source first (token/index.ts:6). The header-sourced token is gated by isAllowedHeaderRequest(headers, payload.config.csrf), where csrf is [BASE_URL] (src/payload.config.ts:104,160).
3. **propagation** `packages/payload-cloudflare-access/src/csrf/index.ts:35` (isAllowedHeaderRequest) — With no Origin and Sec-Fetch-Site 'cross-site', the rule returns true when Sec-Fetch-Dest is 'document', with no path or Sec-Fetch-User condition. Line 33 also returns true for 'same-site' (or absent) fetch metadata with any destination.
4. **propagation** `packages/payload-cloudflare-access/src/strategy/index.ts:65` (authenticateAccess) — After verifyAccessJWT and resolveAccessUser succeed, req.user is the owner with \_strategy 'cloudflare-access'. When the plugin is enabled it is the only strategy, because local auth is disabled.
5. **sink** `node_modules/@payloadcms/next/dist/views/Document/index.js:249` (renderDocument (autosave create-on-render)) — With shouldAutosave, no drafts.validate, no id and a collectionSlug, the render calls payload.create({collection, data: initialData || {}, draft: true, req, user}), inserting an empty draft during the GET render, then redirects to it.

### 根拠

- `packages/payload-cloudflare-access/src/csrf/index.ts:33` — Header rule allows any Origin-less request whose Sec-Fetch-Site is not 'cross-site' (same-site, same-origin, none, or absent), regardless of destination. At line 35 it allows cross-site requests with Sec-Fetch-Dest 'document'.
- `node_modules/payload/dist/auth/extractJWT.js:36` — Baseline Payload 3.84.1 cookie rule rejects Origin-less cross-site requests and requests with no Sec-Fetch-Site (lines 30-37). This is the protection the admin GET-render writes implicitly relied on. It accepts same-site, so the sibling-subdomain variant is baseline-equivalent.
- `node_modules/@payloadcms/next/dist/views/Document/index.js:245` — shouldAutosave = hasSavePermission && hasAutosaveEnabled(...). Line 248 adds !validateDraftData && !idFromArgs && collectionSlug, then calls payload.create on GET (lines 249-271).
- `src/collections/blog.ts:31` — blog uses versions.drafts.autosave with no drafts.validate, and create access is user !== null (blog.ts:27). news.ts:51, works.ts:33, gallery.ts:30 and logs.ts:28 match, so any Access-authenticated user satisfies hasSavePermission and the create-on-render branch.
- `node_modules/@payloadcms/next/dist/views/List/index.js:70` — List view GET render calls upsertPreferences for key collection-<slug> with columns, groupBy, limit, preset and sort taken from query parameters. This is a second GET-render write sink.
- `docs/cloudflare-access.md:58` — Runbook puts napochaan.com/admin* and /oauth/authorize* under an Access path app, so Access injects Cf-Access-Jwt-Assertion on admin requests that carry CF_Authorization.
- `docs/cloudflare-access.md:62` — Runbook sets the CF_Authorization cookie to SameSite=Lax and notes it is still sent on top-level GET navigations. It is also sent on same-site subresource requests, so neither request shape is blocked.
- `packages/payload-cloudflare-access/src/csrf/csrf.test.ts:51` — Tests pin a top-level cross-site GET (Sec-Fetch-Dest document) as allowed, with no path or user-activation condition, confirming the relaxation is host-wide.
- `src/payload.config.ts:160` — csrf is [BASE_URL ?? 'http://localhost:3000'], so the allowlist only matters when an Origin header is present. Origin-less GET navigations bypass it.
- `src/collections/hooks/revalidate/index.ts:103` — createPublishedTagAndPathRevalidateHooks.afterChange only dispatches tag/path revalidation when isPublishedChange(doc, previousDoc) is true, so an empty draft created on render triggers no cache purge or public-site change.

### 未解決の前提（blockers）

- target-controlled execution blocked: host cannot enforce memory, total-disk and per-sandbox process limits required by the execution policy
- CF_ACCESS_TEAM_DOMAIN / CF_ACCESS_AUD are not set in any committed environment (wrangler.toml), so the plugin is currently disabled. Exploitation requires the documented enablement in docs/cloudflare-access.md.
- Deployment and browser facts are not source-visible: whether the Access path app covers /admin* as documented; whether Access injects Cf-Access-Jwt-Assertion on a cross-site top-level GET carrying a Lax CF_Authorization cookie (or after a silent IdP re-auth redirect); the cookie's actual SameSite setting; and for the same-site variant, whether any sibling *.napochaan.com host can serve attacker-controlled markup.
